# Data contract v0.1 → v0.2: what changes and what it means

*Decision 2026-10-10: **option A** approved (whole v0.2). Kept as the record of the comparison.*

*2026-10-10. Full text: `../SPEC.md` (changes marked **[v0.2]**); v0.1 is in git history
(commit d5fe98d). Sources: the cold code review
(`../../../reviews/code_review_S0-S2/SUMMARY.md`, IDs C1–C10) plus one addition of mine
(C11, polygon spatial order).*

## 1. In short

- **Your four v0.1 decisions are unchanged:** the main matrix is the default X; all embeddings are
  kept; display is 2-D with a z filter; polygon holes are dropped.
- **Ordinary single-cell data (h5ad / AnnData):** the storage layout is unchanged. Only the
  rules around it change: the version-compatibility policy, a stricter validator, and a section
  key for multi-sample data.
- **Spatial data:** units for a scale bar (all spatial data). Faster transcripts and cell
  outlines (mainly imaging-based data such as MERSCOPE, Xenium and CosMx). A safe rule for very
  large mask IDs.
- **Timing:** the S5 converter writes only tables, and spatial elements are first written in S6.
  So only the cross-cutting parts must be settled before S5. The transcript and outline parts
  could be decided any time before S6 at no extra cost.

## 2. Measured effect on transcripts (MERSCOPE example `region_1`, 5.6 M transcripts, 500 genes)

Reproduce with `pixi run -e dev python bench/contract_v02_points.py <points.parquet> <tmp_dir>`.
"Useful data" is the x, y values the view actually needs. Downloads are compressed bytes fetched
over HTTP.

| View | Useful data | v0.1 | v0.2 (16,384-row chunks) |
|---|---|---|---|
| One gene, whole tissue: median gene (4,473 points) | 35 KB | 6.9 MB | **0.11 MB** |
| One gene, whole tissue: 90th-percentile gene (24,516 points) | 192 KB | 6.9 MB | **0.33 MB** |
| One gene, whole tissue: average over all 500 genes | 87 KB | 6.8 MB | **0.18 MB** |
| Largest gene (233,706 points), zoomed to 10 % × 10 % of the tissue | 182 KB | 13.7 MB | **0.82 MB** |
| All transcripts, zoomed out (1 M-point sample) | 11.4 MB | 39.4 MB | **6.7 MB** |

The total store size is the same (36.6 MB of coordinates). Files: v0.1 has 6 chunk files; v0.2
has 340 chunks grouped into 6 shard files.

**Chunk-size choice.** On the same data, 65,536-row chunks gave 0.44 MB for a median gene and
32,768-row chunks gave 0.22 MB. 16,384 rows is the best of the three without making very many
small requests.

**At larger scale (estimate).** For a 100 M-transcript Xenium or MERSCOPE run, v0.1 would download
about 7–14 MB per gene switch and **about 650 MB** for the zoomed-out view, since every chunk is
touched. v0.2 stays at about 0.1–0.3 MB per gene and **about 7 MB** for the zoomed-out view,
because those sizes do not grow with the dataset. A gene with tens of millions of points is shown
zoomed out from its 100,000-point sample (~0.8 MB), not in full (hundreds of MB).

## 3. Each change

"Later?" says what happens if the change is postponed:
- **Minor**: can be added later without rebuilding stores.
- **Rebuild**: changing it later means reconverting existing stores of that kind.

| # | Change | Data affected | Why | Cost | Later? |
|---|---|---|---|---|---|
| C7 | **Compatibility rule:** readers ignore unknown fields; the validator stays strict for its own version | **All** | v0.1 rejected unknown fields. The first format update would have made every older server reject every new store | none | **No: must be settled before the first store exists (S5)** |
| §12 | **Stricter validator:** chunking, codec, sorted CSC, names, metadata, spatial order; chunk-by-chunk deep check | **All** (most important for large atlases) | v0.1's validator accepted an X in one huge uncompressed chunk, which would make gene queries as slow as in the old tools. A whole-array deep check would need ~80 GB RAM for a 20 G non-zero atlas | ~0.5 day | Possible, but the S5 converter should be tested against it |
| C5 | **Section key** (`section_keys`) | Multi-section or multi-sample data (e.g. `spatial.h5ad`: embryo / position / z) | Promised in the plan; needed for one-panel-per-section views | small | Minor |
| C6 | **Units** per coordinate system | All spatial data | A scale bar needs to know µm vs pixel | small | Minor |
| C1 | **Transcripts:** 16,384-row chunks in shard files; the redundant per-point `feature` array dropped | Imaging-based (transcript coordinates) | §2: 35–60× less download per gene | none at runtime; the converter sorts as before | **Rebuild** of transcript data |
| C1 | **Transcripts:** stored zoomed-out sample (`overview/`) | Imaging-based | v0.1's sample was a list of positions, so showing it meant downloading every transcript | about +7 MB per dataset | Minor |
| C2 | **Transcripts:** per-gene sample for genes with > 100 k points (`lod/`); box per chunk (`chunk_bbox`) | Imaging-based, large runs | Highly expressed genes stay fast; when zoomed in, only visible chunks are read | ≤ the size of those genes' data; usually a few % | Minor |
| C3 | **Cell outlines:** closed rings, counter-clockwise, 32-bit offsets | Data with segmented outlines (mainly imaging-based) | Lets deck.gl skip a slow per-polygon clean-up pass, and avoids 64-bit numbers the browser cannot use directly | none | **Rebuild** of outline data |
| C11 | **Cell outlines (my addition):** sorted by position, with per-block boxes and cell centroids | Data with segmented outlines, large | 1 M cells × ~40 vertices is ~320 MB if loaded at once. With v0.2, zoomed out draws centroids (8 MB) and zoomed in reads only visible blocks. Not measured yet; to be benchmarked in S6 | none at runtime | **Rebuild** of outline data |
| C4 | **Large mask IDs:** relabelled to 1…N when IDs are 64-bit or very sparse, originals kept | Segmentation masks with unusual IDs | A dense lookup for IDs around 10⁹ would need gigabytes, or IDs could wrap around silently | none for normal masks | Rebuild, only for affected masks |
| C8 | NGFF `image-label` metadata on masks | Segmentation masks | napari and Vitessce then recognise them as label images | none | Minor |
| C9 | Clarifications: downsample dtype, negative mask values, dataset id wording | All | Removes ambiguity | none | Patch |

## 4. Not changed

- **Expression tables:** the gene-by-gene CSC layout, chunk sizes, gene statistics and downsampling
  are the same as v0.1. The reviewers found the table layout sound; only enforcement was missing.
- **Images:** the 512-px tile pyramids are the same.
- **Direct preview (no conversion), transforms, store location:** the same.

## 5. Options

| Option | What you approve now | Effect |
|---|---|---|
| **A (recommended)** | The whole v0.2 draft | Cross-cutting parts are implemented now (~0.5–1 day, before S3/S5). Transcript and outline parts are implemented in S6, where they belong, with the S6 benchmark confirming C11. No rebuilds expected later |
| B | Only the cross-cutting parts (C7, §12, C5, C6, C9) | The same work now. Transcript and outline decisions return to you at S6; nothing is lost by waiting, since no spatial store exists before S6 |
| C | Keep v0.1 | Not recommended: v0.1's compatibility rule breaks on the first format update, and its validator does not enforce the table layout |

A and B differ only in when you decide the spatial parts, not in work or risk now.
