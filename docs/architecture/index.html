canopy Architecture Map
canopy · lab single-cell and spatial data browser

Architecture map

How the code is organised at the end of stage 1 (steps S0–S9 and the review batches), read straight from the source at commit 422ac78. The diagrams show the parts and the main paths through them, the next section how loading and drawing are built for large data; the explorer lists every module with its classes, methods and functions, what each does, and which modules it uses and is used by.

    1 · The whole system

    How the parts fit together

    Three kinds of process work together: the browser app, the canopy serve server, and one worker process per running conversion. The server never sends file paths to the browser and never takes one from it: datasets are addressed by id, converted copies by version. A dataset is shown in one of two ways. The preview path reads the original file on the server, one element at a time. Once a dataset is converted, the browser reads the converted copy itself, by byte ranges, and the server only serves files. Every part writes structured log lines, which reach the developer only through the privacy-filtered bundle.

    3 · Built for scale and speed

    How loading and drawing stay fast as data grows

    The browsers the lab looked at before Canopy (cellxgene, cirrocumulus, SCope and Vitessce) each solve part of this. Canopy combines their best ideas and adds a few of its own, so that a 1–3 M cell atlas, a 55 GB h5ad and 20 spatial sections side by side stay interactive on one shared host. The comparisons below describe each tool's default design as read in its source (see the project's reports 01 and 09), not a benchmark between them.

    Loading data: what the server reads and sends

    StepCanopyWhat others do
    Finding datasetsThe crawler walks the data folders with scandir and fingerprints each file from its metadata only (no values). A rescan skips a file whose size and time stamp did not change, so a share with hundreds of datasets rescans in seconds.cellxgene has no file list (one dataset per process; the gateway starts one per click). cirrocumulus registers datasets one by one. SCope lists a folder of loom files.
    Opening a datasetNothing is loaded up front. A request reads one element (one obs column, two embedding columns, one gene) through h5py or zarr, from a dataset kept open in a cache with a memory budget and an idle timeout. Small files are read whole; datasets too large to read by column are converted.cellxgene loads the whole AnnData into memory per process by default. cirrocumulus reads requested columns in backed mode (the closest to Canopy). Vitessce needs the data converted to zarr beforehand.
    Reading a geneThe fingerprint says how a gene can be read (directly from CSC, from a matrix held in memory, or only after conversion) and how many bytes it costs, before anything is read. Converted copies store the matrix by gene (CSC) with per-gene statistics (non-zeros, mean, max, 99th percentile), so a gene of a 1.65 M cell atlas is one contiguous read.cellxgene and cirrocumulus read a column of X in whatever layout the file has; a cell-wise (CSR) matrix means touching every row block.
    Sending valuesBinary, not JSON. Embeddings as uint16 per column (half of float32, finer than a pixel). Genes sparse or dense, whichever is smaller, quantised to 16 bits with 0 and missing values exact, and whole-number counts exact up to 65,534. Category columns as int8/int16 codes. ETags let the browser reuse what it has.cellxgene sends float32 columns as FlatBuffers. cirrocumulus answers each request with the columns asked for. Vitessce reads zarr chunks directly.
    Big spatial dataThe converted copy holds images as OME-Zarr pyramids (read tile by tile through Viv), cell outlines in blocks of 4,096 with bounding boxes (only the blocks in view are read; centres when zoomed out), and transcripts grouped by gene with a sampled level of detail. The browser reads these files itself with HTTP byte ranges into a chunk cache, so the server is only a file server for them.Vitessce also reads SpatialData zarr and Viv tiles in the browser (Canopy uses Viv for images too). cellxgene, cirrocumulus and SCope do not show segmentation outlines or transcripts.
    Converting large filesIn a separate worker process with a memory reservation and a watchdog. The cell-wise matrix is turned gene-wise out of core: entries are sorted into gene buckets spilled to disk, so a 55 GB h5ad converts within a fixed memory (16 min on the host). Stores are zarr v3, sharded (64 chunks a file) and zstd-compressed, so network storage sees few large files.SCope v2 converts uploads to TileDB-SOMA with Celery; Vitessce leaves conversion to the user (vitessce-python); cellxgene and cirrocumulus do not convert.
    PlotsViolins, composition bars and density maps are computed on the server with numpy.bincount over integer codes (no per-cell data sent) and cached by ETag. Plots of a lasso selection are computed in the browser from values it already has.cirrocumulus computes plots on the server too; cellxgene computes histograms in the browser from full columns.

    Drawing: what the browser does per frame

    StepCanopyWhat others do
    One canvasAll views and panels share one WebGL context: each panel is a deck.gl viewport on one canvas. Browsers allow only about 16 contexts, so this is what lets 24 linked datasets, each split into panels, draw at once.A page with one canvas per view needs one WebGL context each and runs into that limit; cellxgene shows one embedding at a time.
    Colour on the GPUEach cell is one float on the GPU (a category code or a value); a 256-entry lookup texture and a range uniform turn it into a colour in the shader. Changing palette, colour map, range or hidden categories uploads nothing per cell. Colours follow the category name (a stable hash), so the same cell type has the same colour in every view and dataset.cellxgene and cirrocumulus compute colours per cell in JavaScript (as Canopy did until step S4) and hand the renderer new colour arrays when the colouring changes.
    Level of detailLarge datasets are reordered once: a stratified sample first (every category kept), then the rest. Any prefix is a fair sample, so drawing fewer cells means drawing a shorter prefix of the same GPU buffer. The canvas shares a budget of 1 M points among its views, gives more to views zoomed in, and lowers the budget when the input-to-draw delay shows the machine cannot keep up.cellxgene and cirrocumulus draw every cell; with millions of cells, frame time grows with the cell count.
    Linked viewsA linked group shares one colour scheme, computed once per group and handed out as the same object while unchanged; views showing the same coordinates share one scale and pan together. Publishes are batched once per frame, so opening 20 views does not rebuild colours 20 × 20 times.Vitessce links views through its coordination model; cellxgene and cirrocumulus show one dataset at a time.
    Hover and lassoHover picking is gated while the pointer moves fast. The lasso tests points in the panel's own coordinates (spatial transforms included) against a mask in one pass; 215 k of 1.65 M cells select in 0.17 s.cellxgene selects with crossfilter on full columns.

    Measured on the lab's host

    From the three host tests (bundles of 2026-10-13 and 2026-10-14; Apple M2 laptop browser, server on the 144-core host):

    • 16.6 ms median frame while moving with 2–4 views and 3.4 M cells (60 frames/s).
    • 10–15 ms frames while moving in linked groups of 19 and 21 spatial sections; about 20 ms for 19 linked embeddings.
    • 0.17 s median until a view is ready; embeddings of 0.5 M+ cells ready in 0.87 s for 90 % of views (target 3 s).
    • Gene requests answered in at most 225 ms by the server (on local disks, 57 ms); 90 % of gene switches under 0.31 s for atlases above 1.2 M cells (target 1 s).
    • Lasso on 1.65 M cells: 23–165 ms. Server memory at most 0.6 GB while serving.
    • Conversions: spatial sections in 5–38 s at ≤ 3.4 GB; a 1.65 M cell h5ad in 10 min at 14 GB; a 55 GB h5ad in 16 min.
